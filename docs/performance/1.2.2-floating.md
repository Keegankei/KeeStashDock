# 1.2.2 floating-panel performance record

The revision-5 candidate reduces the work performed by card proximity updates and changes panel rotation to deliberate drag inspection. Ordinary pointer movement still highlights nearby cards; it no longer rotates the entire panel.

These are local diagnostic observations from 15 October 2026, not a frame-rate guarantee or a cross-device benchmark. The revision-4 baseline was recorded at 20:57:59 Hong Kong time (12:57:59 UTC). The final revision-5 run was recorded at 22:01:22 Hong Kong time (14:01:22 UTC).

## Method

The opt-in [performance fixture](../../tests/KeeStashDock.Desktop.Tests/FloatingPerformanceScenarios.cs) runs real WPF `QuickPanelWindow` controls with 12 synthetic text snippets and an injected pointer. It does not start the product application's global hooks, read user data, or move the operating-system mouse.

- Panel sizes: 400 × 600 and 600 × 900 device-independent pixels.
- Environment: Windows, .NET 10.0.13, WPF rendering tier 2, 150% DPI, 20 logical processors, system animations enabled, high contrast disabled.
- Each scenario receives a 500 ms warm-up followed by approximately four seconds of measurement. These are single runs; results are not averages across repeated benchmark runs.
- The fixture requests an explicit pointer update every 32 ms while normal product timers remain enabled. Delivered sample counts depend on dispatcher load.
- Update time covers the explicit update and small sample bookkeeping. Allocation measures managed bytes allocated on the calling UI thread around that sample; it excludes deferred rendering work on other threads.
- A background timer posts an input-priority dispatcher callback every 16 ms, with at most one pending callback. Queue delay includes thread scheduling and dispatcher servicing, not hardware-input-to-display latency.
- `CompositionTarget.Rendering` observations are UI rendering events, **not presented frames or FPS**. Process CPU and allocation totals in the raw output include the fixture and all process threads.

Local raw outputs are `artifacts/performance/r4-baseline.json` and `artifacts/performance/r5-inspection.json`. The `artifacts` directory is intentionally ignored by Git; the measurements relevant to this record are retained below.

## Recorded results

Allocation is the mean number of bytes per explicit update, rounded to the nearest byte. Times are milliseconds. The old fixed-angle case is included because it provides a closer comparison for card feedback than comparing automatic rotation with the new drag gesture.

| Panel size (DIP) | Revision and scenario | Mean update (ms) | Mean allocated bytes/update | Input queue P95 (ms) |
| --- | --- | ---: | ---: | ---: |
| 400 × 600 | r4: automatic pointer follow | 22.109 | 11,343,832 | 138.549 |
| 400 × 600 | r4: fixed angle, pointer moving | 21.490 | 11,311,847 | 93.031 |
| 400 × 600 | r5: ordinary pointer proximity | 0.203 | 26,874 | 0.800 |
| 400 × 600 | r5: fixed angle, pointer moving | 0.225 | 26,866 | 0.755 |
| 400 × 600 | r5: active drag inspection | 0.041 | 1,401 | 17.540 |
| 600 × 900 | r4: automatic pointer follow | 51.214 | 26,570,549 | 257.450 |
| 600 × 900 | r4: fixed angle, pointer moving | 49.240 | 26,551,741 | 244.517 |
| 600 × 900 | r5: ordinary pointer proximity | 0.231 | 30,496 | 0.989 |
| 600 × 900 | r5: fixed angle, pointer moving | 0.207 | 30,035 | 1.173 |
| 600 × 900 | r5: active drag inspection | 0.031 | 1,400 | 17.349 |

The final drag fixture calls `BeginInspection`, repeatedly calls `MoveInspection`, and verifies that the update path produces more than ten distinct panel angles. Both panel sizes recorded 51 distinct yaw values. Ordinary pointer proximity and fixed mode each recorded one angle, as intended.

The old follow gesture and new drag gesture perform different work and have different input semantics. Their rows must not be presented as an equivalent-workload FPS comparison. The much lower explicit update cost also does not account for the complete cost of drawing and presenting the tilted panel. In particular, the measured drag input-queue P95 remains about 17.5 ms even though its explicit pose update is much shorter.

The stationary r5 fixture recorded input-queue P95 values of 47.129 ms and 45.128 ms for the smaller and larger panels. That fixture still runs its own sampling timer, latency timer, and rendering-event subscription. Those observations do not establish normal product idle latency, CPU usage, or power consumption.

## Implementation changes

- Card feedback uses projected card polygons, cached button references, a shared inverse projection, and transforms within the two-dimensional content tree. It avoids repeated WPF hit tests and expensive transforms across the 2D/3D boundary during proximity sampling. Normal WPF control input remains intact.
- Repeated pointer positions skip proximity recalculation. Pointer events wake the sampler instead of performing duplicate work immediately; the sampler stops after motion settles. Active inspection samples the drag explicitly and keeps the last angle when released.
- Pose changes update yaw, pitch, and offsets together, then rebuild the projection once. During a captured inspection drag, the 3D child tree does not need repeated hit testing; normal hit testing resumes when inspection ends.
- The perspective host reuses its live control texture where it fits the cache limit and avoids unnecessary viewport clipping. The control instances, bindings, and editable content are retained.
- Card layers retain their drawing resources. Panel shadows reuse falloff brushes and pens and avoid unnecessary outline cloning. Layered shadows remain enabled.

The final solution test run passed 500 tests, with one skipped test, out of 501. Functional checks include rendered transparency, control interaction, inspection gestures, card feedback, settings persistence, and edge docking. Physical mouse behavior, visual comfort, and performance on other GPUs and monitor configurations still require normal release-candidate acceptance.

## Reproduce

Run from the repository root on Windows after restoring dependencies:

```powershell
dotnet build tests/KeeStashDock.Desktop.Tests/KeeStashDock.Desktop.Tests.csproj -c Release --no-restore -m:1
$env:KEESTASHDOCK_PERF_OUTPUT = Join-Path (Get-Location).Path 'artifacts/performance/floating-local.json'
& '.\tests\KeeStashDock.Desktop.Tests\bin\Release\net10.0-windows\KeeStashDock.Desktop.Tests.exe' --filter 'FullyQualifiedName~SettingsTranslationTests' --progress off --timeout 120s
Remove-Item Env:KEESTASHDOCK_PERF_OUTPUT
```

The probe is disabled when `KEESTASHDOCK_PERF_OUTPUT` is absent. Timing values are recorded for inspection rather than enforced as wall-clock pass/fail thresholds.
